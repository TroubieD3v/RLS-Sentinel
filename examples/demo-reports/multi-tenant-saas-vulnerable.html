CONFIGURATION RISK RLS-009 · SECURITY DEFINER misuse candidate · Needs triage

SECURITY DEFINER function public.get_invoice(p_id uuid) (owner app_owner) can be executed by app_alice, app_anon, app_bob, app_charlie, app_support, app_user… and PUBLIC; its owner bypasses RLS on protected tables.

Severity rationale: Candidate only: SECURITY DEFINER + owner bypasses RLS + callable by other roles. Function bodies are not analysed, so leakage is unproven. search_path is NOT pinned.
Provenance: CATALOG_FACT, STATIC_INFERENCE · Confidence: CONDITIONAL · Subject: public.get_invoice(p_id uuid)

Why it matters. The function body runs with the owner's rights; if it reads tenant tables without checking the caller, RLS is bypassed through the function. Without a fixed search_path, object resolution is also hijackable.

Remediation (review first). Prefer SECURITY INVOKER. If DEFINER is required: ALTER FUNCTION public.get_invoice(p_id uuid) SET search_path = pg_catalog, public; REVOKE EXECUTE ON FUNCTION public.get_invoice(p_id uuid) FROM PUBLIC; and check the caller's tenant inside the body.

Limitations. Not all SECURITY DEFINER functions are vulnerable. Add an EXECUTE expectation to confirm behaviour at runtime.
