# RLS Sentinel

**Доступ к базе данных. Проверенный.** · [English](README.md)

RLS Sentinel проверяет, делают ли ваши политики Row-Level Security в PostgreSQL то, что вы от них ожидаете. Он не
ограничивается чтением текста политик: он **выполняет** матрицу авторизации (кто может читать / вставлять /
изменять / удалять какие строки под какой ролью БД) во временном экземпляре PostgreSQL и по каждому случаю
сообщает, что PostgreSQL сделал на самом деле, с доказательствами. Всё, что доказать нельзя, помечается как
`INCONCLUSIVE` или `UNSUPPORTED` и никогда не считается безопасным.

> **Права доступа — не доказательство. Проверяйте их.**

## Что умеет

| Возможность | Как работает |
|---|---|
| **Поведенческие тесты** | Каждое ожидание из YAML-спецификации превращается в реальный SQL, выполняемый как `SET LOCAL ROLE <актор>` в транзакции, которая всегда откатывается. Логин харнесса — не суперпользователь, `NOINHERIT`, без `BYPASSRLS`. |
| **Доказательства, а не мнения** | Для каждого случая записываются решающий барьер (SQL `GRANT` или RLS), применимые политики, флаги роли (superuser / `BYPASSRLS` / владелец / `FORCE`), SQLSTATE и маскированный признак строки. Содержимое строк не сохраняется. |
| **Аудит каталога живой БД** | `rls-sentinel scan` читает `pg_catalog` в read-only сессии: без DDL, без DML, без данных строк. 21 правило (RLS-001…021) даёт статические находки, которые всегда помечены как *вывод*, а не *подтверждение*. |
| **Матрица авторизации и граф доступа** | Идентичности × операции × ресурсы строятся только из выполненных случаев; типизированный граф ролей, членств, грантов, политик, представлений и функций с происхождением каждого ребра. |
| **What-if Policy Lab** | Черновик изменения политики воспроизводится в одноразовом клоне, затем сравнивается вся матрица: исправлено, регрессии, расширенный доступ. Черновики проходят allow-list на уровне AST; в исходную БД ничего не применяется. |
| **Отчёты** | JSON, Markdown, HTML, CSV и **SARIF 2.1.0** (проверен по официальной схеме), а также сгенерированный pytest-набор регрессионных тестов. |
| **Дрейф** | Сравнение двух снимков или запусков; семантический дифф политик с направлением риска. |


## Быстрый старт

Нужны Python 3.12+ и установленный PostgreSQL 15+ (используются только его бинарные файлы для запуска
одноразового кластера) **или** Docker.

```bash
python scripts/build_release.py                          # собирает UI и wheel в dist/ (нужен Node 22+)
pip install dist/rls_sentinel-1.0.0-py3-none-any.whl
rls-sentinel demo up                                     # локальный UI на http://localhost:8787, синтетические фикстуры
```

Репозиторий не публикует пакет в PyPI; артефакты релиза (wheel, sdist, контрольные суммы, SBOM) создаёт
workflow релиза.

Только командная строка:

```bash
rls-sentinel fixtures list
rls-sentinel test --fixture multi-tenant-saas --variant vulnerable --format html -o report.html
echo $?    # 1: найдены подтверждённые нарушения
rls-sentinel test --fixture multi-tenant-saas --variant secure --format sarif -o results.sarif
echo $?    # 0
```

Docker Compose (API + UI + база метаданных + защищённая внутренняя одноразовая база для фикстур):

```bash
python scripts/make_env.py          # создаёт .env со случайными секретами (в git не попадает)
docker compose up --build
# откройте http://127.0.0.1:8787 и вставьте SENTINEL_API_TOKEN из .env в диалог Unlock
```

## Встроенные фикстуры

Все данные синтетические. В каждой фикстуре есть вариант `vulnerable` с документированными дефектами и вариант
`secure` — отрицательный контроль (он обязан давать ноль подтверждённых нарушений).

| Фикстура | Что показывает |
|---|---|
| `multi-tenant-saas` | политики по командам, права на столбцы, default-deny, `security_invoker` против представлений владельца, `SECURITY DEFINER` |
| `policy-precedence` | permissive и restrictive, `PUBLIC`, обход владельцем и `FORCE`, `BYPASSRLS`, таблица только с restrictive-политикой |
| `saas-auth-context` | `auth.uid()` / claims в стиле Supabase (синтетическая идентичность, помечена как таковая) |
| `external-benchmark` | пример `passwd` из документации PostgreSQL; ожидания взяты из документации |

Измеренное совпадение с документированными ожиданиями на PostgreSQL 15, 16, 17 и 18 — в
[docs/benchmarks.md](docs/benchmarks.md), там же тест масштаба: сгенерированная схема из 1 000 таблиц, 10 000 политик
и 4 000 поведенческих случаев проходит целиком примерно за 27 с на одной машине и находит ровно 65 заложенных нарушений. Это проверка согласованности на маленьких синтетических схемах, а **не**
показатель обнаружения.

## Использование на своей схеме

1. Подготовьте каталог фикстуры: схема и политики в SQL, синтетические данные и спецификация ожидаемых политик
   (см. [docs/authorized-testing.md](docs/authorized-testing.md)). Запуск: `--fixture ./my-fixture --trust-fixture`
   (SQL выполняется суперпользователем в одноразовом сервере — запускайте только то, что написали или проверили сами).
2. Для живой БД, которую вы **вправе** проверять, создайте непривилегированный логин-инспектор и выполните
   `rls-sentinel scan --connection-env SOURCE_DSN --allow-target db.internal` — это read-only аудит каталога.

Поведенческие тесты против исходной БД не запускаются никогда. Это осознанное решение, а не недоработка.

## Честные ограничения

- Результат описывает *проверенную схему в одноразовой БД* на ролях PostgreSQL. Это не доказательство ничего о
  аутентификации вашего приложения, пуллере соединений или о том, могут ли клиенты подделывать настройки сессии.
- Покрытие = `(PASS + FAIL) / ожидаемые проверки`. Операции, для которых нет ожиданий, не покрыты; продукт так и
  говорит, а не показывает 100%.
- Статические находки — это вывод по тексту каталога; возможны ложные срабатывания и пропуски.

Полный список: [docs/limitations.md](docs/limitations.md).
